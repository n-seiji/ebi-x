# Slackでスライドを作成・修正・納品する

依頼から原稿を作り、同じスレッドでプレビューを見せながら修正を重ね、ユーザーがOKした版だけを編集可能なpptxにして納品する。

## 前提

- slidesリポジトリは `EBIX_WRITABLE_ROOTS` に含まれ、作業ターンのプロンプトに「元のパス → スレッド専用クローン」として示される。作業は必ずそのクローンで行い、元のパスや別スレッドのクローンには触れない。
- 原稿の書き方・デザイン規約・ビルドの出力先は、クローン内の `README.md`、`docs/workflow.md`、`scripts/build.sh` を読んで従う。このplaybookと食い違う場合は、承認ゲートに関する事項を除きslides側の規約を優先する。
- Slackへの添付は、作業ターンの最終応答に置く「## 添付ファイル」見出しでbotに依頼する。自分でSlackへ送信しない。
- mainへのpush・merge、Google Slidesへの公開はしない。作業用ブランチのpushも依頼された場合だけ行う。

## 版の記録

スレッドの作業ディレクトリ（cwd）に `slides-state.md` を置き、次を記録する。同じスレッドの後続の依頼では、最初にこのファイルを読んで対象原稿と最新版を引き継ぐ。

- 対象: slidesクローン内の原稿ディレクトリ（例: `個社提案/<案件名>`）
- 版の一覧: 版番号（v1, v2, …）、その版の原稿をコミットしたハッシュ、提示日時、変更の要約、添付したプレビューのパス
- 承認: 承認された版番号とコミットハッシュ、承認したSlackユーザーと発言の要旨。未承認なら「未承認」
- 納品: 納品したpptxのパスと、元にした版番号・コミットハッシュ

版はクローンの作業用ブランチへのコミットで固定する。プレビューを作るたびに原稿をコミットし、そのハッシュを版として記録する。ファイルが見つからない、または内容が食い違う場合は推測で補わず、ユーザーに確認する。

## 1. 新規作成（「○○のスライドを作って」）

1. 依頼・スレッドに書かれた情報は聞き直さない。対象（社名・目的・枚数感など）が決められない場合だけ、1回に1問だけ質問してターンを終える。
2. slidesの手順に沿って原稿ディレクトリを作り、原稿を書く。承認前なので `status: approved` にはしない。
3. 原稿をコミットし、v1として `slides-state.md` に記録する。
4. 下書きのプレビューを作る。

   ```sh
   pnpm build "<対象ディレクトリ>" images --draft
   pnpm build "<対象ディレクトリ>" pdf --draft
   ```

5. 生成されたファイルをcwd配下の `previews/v1/` にコピーする。ページ画像が多い（目安5枚超）場合は、全ページを並べた一覧画像を1枚作り、個別ページの画像は代表的な数枚に絞る。全ページPDFは必ず添付する。
6. 最終応答には、版番号（v1）、構成の要約、確認してほしい点、「修正点を返信するか、この版でよければ『v1でOK』と返信してください」を書き、「## 添付ファイル」に一覧画像（または各ページ画像）と全ページPDFの絶対パスを並べる。

## 2. 修正（「3ページ目を短くして」）

1. `slides-state.md` から対象原稿と最新版を読み、そのクローンの原稿を修正する。別の原稿を新しく作らない。
2. 修正をコミットし、新しい版番号（v2, v3, …）で記録する。承認済みの版を修正した場合も新しい版とし、承認は未承認に戻す。
3. 新規作成と同じ手順で `previews/v<N>/` にプレビューを作り、変更点の要約と版番号を添えて添付する。

## 3. 承認と納品（「この版でOK、確定して」）

- 承認として扱うのは、提示済みの版に対するユーザーの明示的な発言（「v2でOK」「この版で確定して」など）だけ。最初の作成依頼、無回答、時間経過、修正依頼、生成・添付の完了、botや他人のリアクションは承認ではない。
- 「この版」が指す版が最新版と異なる、または判別できない場合は、どの版かを1問で確認してターンを終える。
- 承認された版のコミットがクローンの `HEAD` で、作業ツリーに未コミットの変更がないことを確認する。違う場合は納品せず、状況を伝えて確認する。
- 承認を `slides-state.md` に記録してから、個社提案では原稿を `status: approved` にしてコミットし、通常のビルドを行う。承認の記録より前に `status: approved` にしない。既存の承認ゲートを迂回するオプションやスクリプトの改変はしない。

  ```sh
  pnpm build "<対象ディレクトリ>"
  ```

- pptxはPDFから変換されるため、納品前にpptxを画像化するなどしてレイアウト崩れ（文字のはみ出し・欠落、フォント置換、画像のずれ）を確認する。崩れていれば納品せず、内容と対処案をユーザーに伝える。
- 問題がなければpptxを `deliverables/` にコピーし、納品の記録を `slides-state.md` に追記して、「## 添付ファイル」でpptxを添付する。本文には元にした版番号を書く。
- 承認後に修正を依頼された場合は「2. 修正」に戻り、新しい版として再度承認を得る。

## 4. 添付の再送（「添付を再送して」）

- botが添付に失敗したと伝えた場合、成果物は作業領域に残っている。`slides-state.md` と前回のパスを確認し、ファイルを作り直さずに「## 添付ファイル」で同じファイルを指定する。
- ファイルが無くなっている場合だけ、記録された版のコミットから作り直す。作り直したことを本文に書く。

## 禁止事項

- ユーザーの明示的な承認前に、通常ビルドのpptxを作成・添付しない。
- 別スレッドのクローン・作業ディレクトリ・`slides-state.md` を読み書きしない。
- 作業ディレクトリ内のファイルを一括で添付しない。依頼に関係するプレビュー・PDF・pptxだけを明示する。
- 認証情報や `.env` の内容を原稿・添付・Slackの本文に含めない。

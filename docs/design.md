# 設計

ebi-x の決めごとと、その理由をまとめます。細かな動き（上限値、ファイル名、変数の一覧）はコードを見てください。

## 方針

- **小さく保つ**：Go の単一バイナリ、単一プロセス。Web UI、DB、HTTP の Events API は持ちません。設定は `.env`、状態は `data/` の JSON ファイルです。
- **考えるのも作業するのも Codex**：bot は Slack とのやり取り、許可、状態、隔離だけを受け持ち、依頼の中身の判断は Codex に任せます。
- **bot と Codex の境界は出力契約**：Codex は Slack・状態ファイル・メモリに直接触れません。最終応答に決まった見出しを書き、bot がそれを読んで処理します。
- **副作用のある作業は自動でやり直さない**：重複して投稿するのは許しても、結果を失うことと、作業を二重に実行することは避けます。

## 構成

```text
cmd/ebi-x/            起動、設定の読み込み、シグナル処理
internal/
  config/             .env の読み込みと検査
  slackbot/           Slack のイベント処理と、会話の後に動く仕組み
  codex/              codex exec の起動と出力の解析
  prompt/ policy/     Codex へ渡すプロンプトと最上位ルール
  state/              data/state の JSON ストアとプロセスロック
  workspace/          スレッドごとの作業ディレクトリとクローン
  memory/ playbook/ usersettings/   記憶
  attachment/         添付ファイルの検査
  github/             PR の読み取りと認証情報
  slackfmt/           Slack 向けの分割と整形
```

## 依頼の処理

```text
Slack イベント ──ACK── 許可の確認 ── 受付（ClaimEvent）── 👀
   └─ スレッドのロック ── 同時実行枠 ── received → working ── codex exec
        └─ 出力契約の処理（添付、予定、見守り、メモ…）── 本文を投稿 ── ✅/❌/🙋
```

- イベントは内容にかかわらずすぐ ACK します。遅れると Slack が再配信するためです。
- 受付は mention ごとに1回だけ通します。同じイベントが2回届いても二重に作業しないためです。
- Slack スレッドごとに Codex セッションを1つ持ち、参加者全員で使います。作業原則・ルール・メモリ・playbook の一覧は最初の依頼でだけ渡すので、それらの変更は次に始まるスレッドから効きます。
- 人の入力はブロックに分けて渡し、その中の指示がルールや契約を変えられないことを `policy.md` で示します。

### 状態

```text
received ──→ working ──→ done
    │            └────→ interrupted
    └──→ failed（再受付できる）
```

- `failed` は Codex を起動する前の失敗なので、受け付け直せます。
- `interrupted` は作業が副作用を残したかもしれない失敗なので、終端にして自動ではやり直しません。起動時に `working` のまま残っていたものもここに入ります。
- 回答待ちは `done` です。作業は失敗していないためです。

## 作業場所の隔離

スレッドが並列に動いてもファイルが衝突しないよう、作業ディレクトリと Git リポジトリのクローンをスレッドごとに分けます。元のリポジトリは読み取り専用のままです。

- クローンは変更が必要になるまで作りません。読むだけの依頼でクローンの時間を払わないためです。
- git worktree ではなく、git ディレクトリを `.gitdir` に分けたクローンを使います。Codex のサンドボックスは `.git` という名前のディレクトリを常に読み取り専用にするので、worktree ではコミットできません。
- クローンはオブジェクトをハードリンクで共有しません（`--no-hardlinks`）。`.gitdir` は Codex が書けるので、共有すると元のリポジトリのオブジェクトを書き換えられるためです。
- Git リポジトリでない writable root と `data/playbooks` は全スレッド共有で、同時に書くと後勝ちです。

## Codex から守るもの

Codex のコマンドは、禁止しなければファイルシステム全体を読めます。そのため、状態・メモリ・`.env`・`CODEX_HOME`（認証情報と全スレッドの履歴を含む）・既知の認証情報の置き場を、すべての実行で読み書きともに禁止します。push と署名に要る置き場だけは、起動時に git の設定から調べて外します。

- ほかのスレッドの作業ディレクトリは列挙して禁止しません。禁止ルールがスレッドの数だけ増えると、いずれ引数の上限を超えるためです。
- Codex のプロセス環境は許可リストです。拒否リストでは、運用者のシェルにある `DATABASE_URL` などを漏らさない保証ができないためです。
- GitHub App を設定したときは、作業ごとに発行したトークンだけを作業専用のディレクトリに置き、終わったら失効させます。秘密鍵は bot だけが読みます。
- 禁止の一覧が長すぎるときは、切り詰めずに実行しません。

残るリスク：既定の置き場はホーム直下の固定パスなので、`XDG_CONFIG_HOME` などで移したものは `EBIX_DENIED_READ_PATHS` に足します。作業から Docker ソケットに届くと禁止を迂回できます。push に要る `~/.ssh` や `~/.config/gh` は、ネットワークに出られる作業から見えます。

操作ルール（何の前に確認するか）はプロンプトでの指示で、ここでの禁止とは別です。

### 閉じたチャンネル

プライベートチャンネル（グループ DM を含む）と Slack Connect チャンネルを「閉じたチャンネル」として扱い、次の2つを守ります。

1. 閉じたチャンネルの内容は、ほかのチャンネルの作業から読めない
2. 閉じたチャンネルの作業は、Slack をそのチャンネルの中しか調べられない

- 作業場所を `data/closed/{channel}` に分け、開いたチャンネルの作業からは丸ごと禁止します。禁止ルールはスレッドではなく閉じたチャンネルの数だけ増えます。
- 閉じたチャンネルの作業では Slack の MCP を止めます。MCP の検索範囲をチャンネルで絞る手段がないためです。
- 種類を確かめられなかったときは閉じたチャンネルとして扱います。開いていると誤るほうが危ないためです。
- 承認チャンネルは運用者のチャンネルなので、プライベートでも開いたチャンネルとして扱います。
- 閉じる前に始まったスレッドは、セッションとクローンが元のパスを指しているので、開いた置き場所のまま使います。
- 残るリスク：`/tmp` など Codex の既定の書き込み先はスレッドで分けていません。Slack 以外の MCP は、チャンネルごとの設定で絞らない限り使えます。

### チャンネルごとの設定

`data/channel-rules/channels.yaml` の指示と制限は、依頼のたびに読んで `developer_instructions` と実行の設定に反映します（書き方は [setup.md](setup.md#チャンネルごとの設定)）。

- 承認チャンネルの作業だけが書けて、ほかの作業からは読めません。チャンネル ID やそのチャンネル向けの指示が書かれるためです。
- `github: false` だけでは、ホストの `~/.ssh` を使った push は止まりません。確実に止めるなら `read_only` と組み合わせます。
- ファイルが読めないときは、承認チャンネル以外の依頼を始めません。制限が外れたまま動かないためです。承認チャンネルはファイルなしで動くので、そこで直せます。

## 出力契約

Codex は最終応答に次の見出しを書いて bot に処理を頼みます。行頭の見出しだけを数え、コードブロックの中は数えません。書式が正しくないときは処理せず、その旨を本文の後に出します。

| 見出し | bot がすること |
| --- | --- |
| `## 作業用クローン要求` | スレッド専用クローンを作り、同じセッションに続きを頼む |
| `## 回答待ち` | 🙋 を付け、依頼者に質問を表示する |
| `## 添付ファイル` | 検査してから Slack にアップロードする |
| `## フォローアップ` | 予定を保存し、時刻になったら同じセッションを再開する |
| `## 定期実行` | 定期実行を保存・停止する |
| `## リマインダー` | リマインダーを保存・取り消す |
| `## PR の見守り` | 見守りを始める |
| `## playbook メモ追記` | playbook のメモに日付付きで1行足す |
| `## 全体メモリ追記` | 全体メモリに足す |
| `## 個人設定` | 発言者の個人設定として保存する |

- 定期実行、リマインダー、個人設定は、人の依頼への回答のときだけ受け付けます。人のいないところで予定や設定が増えないようにするためです。
- playbook メモと全体メモリは承認チャンネルからだけ受け付けます。全チャンネルの依頼がこれらを読むためです。
- 添付できるのは、そのスレッドの作業場所にある通常のファイルだけです。シンボリックリンクやハードリンクを通して、ほかの場所のファイルを送らせないためです。

## 記憶

| 範囲 | 置き場所 | 内容 |
| --- | --- | --- |
| 作業の手順 | playbook とそのメモ | 特定の作業の進め方、判断基準、確定した事実 |
| ebi-x 全体 | `data/memory/MEMORY.md` | どの playbook にも属さない技術・運用の事実 |
| スレッド | Codex セッション | スレッドの経緯。別に保存しない |
| 個人 | `data/memory/users/{user}/settings.md` | 本人が頼んだ返答の仕方 |

- チャンネルごとの記憶は持ちません。playbook は作業手順書で、チャンネルの情報置き場には使いません。
- bot だけが記憶を読み、プロンプトに入れます。Codex は記憶のファイルを読み書きできません。
- 個人設定は、そのときの発言者の分だけを毎回添えます。前の発言者の設定が残らないようにするためです。

## 会話の後に動く仕組み

フォローアップ、定期実行、リマインダー、PR の見守り、利用枠、`:done:` の監視は、次の回を先に保存してから実行します。落ちても2回は実行しないためです。どれも実行の前に依頼者とチャンネルがまだ許可されているかを確かめ、人の発言なしに続く回数に上限を置きます。

## Slack への投稿

- 投稿の失敗は 5xx と 429 のときだけやり直します。投稿してから状態を保存するので、落ちたときは重複投稿になることがありますが、結果は失いません。

## 終了とリロード

- SIGINT と SIGTERM では受付を止め、実行中の作業の終わりを待ってから終了します。
- SIGHUP では、新しいバイナリを `-check-config` で確かめてから、実行中の作業の終わりを待って同じパスのバイナリを `exec` します。待つ間に届いた依頼は保存して、再起動後に始めます。使い方は [setup.md](setup.md#9-運用) にあります。
